App Secret

Secret

Never sent with normal API requests

Access Token (this is what the API actually uses)

Bearer credential

Expires

2. What your system actually uses

Your implementation correctly uses access tokens only for API calls.

Token types you may encounter
Token type	Used for	Production suitability
Human User Token	Interactive setup	⚠️ Setup only
System User Token	Background / automation	✅ Required
Page Token	Page publishing	❌ Not for catalogs
App Token	Token introspection only	⚠️ Limited use

Your code explicitly prefers System User access tokens, which is what Meta recommends for production.

3. How credentials are handled in your system (step-by-step)
Step 1: Token is created by Meta (not by your app)

The token is generated via:

Meta Developer Dashboard

Business Manager → System User → Generate Token

Your application never generates tokens itself.

Step 2: Token is provided to the app (operator action)

The operator pastes the token into the UI.

Important security rule you follow:

The token is never written to disk

The token is never logged

The token is never echoed back

Step 3: Token is stored in memory / environment only

Your implementation stores tokens in:

Environment variables (process-level)


This means:

Token disappears when the process exits

No accidental persistence

No plaintext credential files

This is the correct pattern used by production Meta integrations.

Step 4: Token is validated via /debug_token

Before being trusted, the token is introspected using:

GET /debug_token


This verifies:

Token validity

Expiration time

Token owner

Granted permissions (scopes)

Token type (human vs system)

If validation fails:

The token is rejected

No API calls are attempted

Step 5: Token health is cached (safely)

To avoid rate limits:

Token health is cached briefly (TTL)

Cache contains metadata only, never the token itself

This reduces calls to Meta while preserving safety.

Step 6: Token is attached to API requests

Each API call includes the token like this:

Authorization: Bearer <ACCESS_TOKEN>


or as a query parameter:

access_token=<ACCESS_TOKEN>


This is standard OAuth 2.0 bearer-token behavior.

4. What is explicitly NOT done (by design)

Your system intentionally does not:

❌ Store tokens in config files

❌ Encrypt tokens and persist them anyway

❌ Auto-refresh tokens

❌ Share tokens between processes

❌ Convert tokens into “API keys”

❌ Fall back to scraping if token fails

Each of these would violate Meta best practices or increase risk.

5. Why Meta does NOT use API keys

Meta avoids API keys because:

Permissions must be granular and revocable

Business assets change ownership

Access must expire

Abuse must be traceable to a user or system

OAuth access tokens solve all of these problems; static keys do not.
